Identity contract

Keep stable identity separate from visible position

A position answers “where is this item now?” A stable key answers “which item is this?” Removing or reordering an earlier fieldset may change the first answer but never the second.

Key, position, and backend name

Concept Example May change after removal?
Stable key contact-2088 No
Visible position Contact 2 Yes
Author-controlled name contacts[contact-2088][phone] No

Saved items keep server names

Initialization preserves an existing server key and its control name exactly:

<fieldset
  data-a11y-repeatable-fieldset-item
  data-a11y-repeatable-fieldset-key="contact-2088"
>
  <label for="contact-2088-phone">Telephone</label>
  <input
    id="contact-2088-phone"
    name="contacts[contact-2088][phone]"
  >
</fieldset>

Templates opt into generated identity

The only template token is __A11Y_REPEATABLE_KEY__. The author chooses the surrounding backend-compatible shape:

<label for="contact-__A11Y_REPEATABLE_KEY__-phone">
  Telephone
</label>
<input
  id="contact-__A11Y_REPEATABLE_KEY__-phone"
  name="contacts[__A11Y_REPEATABLE_KEY__][phone]"
>

A generated key such as item-1 produces contacts[item-1][phone]. The bracketed convention is an example, not a required server parser.

Removal does not compress names

Suppose a form submits these fields:

contacts[contact-1042][name]=Ada
contacts[contact-2088][name]=Grace
contacts[item-1][name]=Lin

After removing contact-1042, Grace becomes visible Contact 1 and Lin becomes visible Contact 2. Their submitted names remain:

contacts[contact-2088][name]=Grace
contacts[item-1][name]=Lin

Radio groups use the stable key

Radios inside one template item share a tokenized name. Each generated item therefore becomes an independent browser radio group:

<input
  type="radio"
  name="contacts[__A11Y_REPEATABLE_KEY__][method]"
  value="email"
>
<input
  type="radio"
  name="contacts[__A11Y_REPEATABLE_KEY__][method]"
  value="telephone"
>

Accessibility connection

  • Stable tokenized IDs keep each generated label and description associated with its own control.
  • Visible position markers may update so legends remain understandable after structural changes.
  • Names and IDs never use current position as persistent identity.
  • Removed keys remain reserved for the active instance lifetime and are not silently reused.
  • See the saved-items demo and complex-fields demo for executable examples.
