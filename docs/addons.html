Opt-in extension contract

Addons and integrations

Addons are explicit, synchronous hooks supplied through the core addons option. Core behavior does not depend on an addon, and importing the package never registers one automatically.

Validation Bridge, Legend Sync, Remove Guard, Accessible Reorder, Duplicate Item, Undo Remove, and Form Memory Bridge are implemented concrete addons. Each is separately exported, never enabled by default, and absent from the main runtime entry. Reset Structure policy remains explicitly planned.

Validation Bridge

Import createValidationBridge from a11y-repeatable-fieldset/addons/validation-bridge. Its synchronous registerItem adapter runs once for each existing or added item and may return cleanup that unregisters controls and removes adapter-owned errors and summary links before detachment.

The subpath imports no validator, creates no structural live region, and leaves Add/Remove focus to core. See the live-validation, error-summary, and no-submit error-review demo plus compatibility guidance.

Form Memory Bridge

Import createFormMemoryBridge from a11y-repeatable-fieldset/addons/form-memory-bridge. Its custom draft-control adapter stores stable keys and order only, while its explicit initializer prepares missing trusted-template fieldsets before core discovery.

The application supplies the public createRepeatableFieldset factory so the addon bundle does not embed a second core registry. Storage, values, restore consent, expiry, sensitive-field rules, clear UI, and the draft instance remain application-owned. Try the executable two-phase structure demo and A11yFormDraftPersistence integration outline.

Accessible Reorder

Import createAccessibleReorder from a11y-repeatable-fieldset/addons/accessible-reorder. The addon renders native Move up and Move down buttons in one empty owned target per item, then delegates every structural change to public instance.move().

Core owns DOM and registry order, positions, snapshots, focus, announcements, rollback, typed boundaries, and the completed item-moved event. Stable keys, names, IDs, values, and addon registration never change. Boundary buttons remain enabled so activation can keep focus valid and provide one polite already-first or already-last message.

Legend Sync

Import createLegendSyncAddon from a11y-repeatable-fieldset/addons/legend-sync. It appends one deliberately marked, committed control value to a dedicated text-only suffix inside each item's existing legend while preserving the generic label and visible position.

The addon updates only on change, creates no live region or focus move, and rejects hidden, password, file, authentication-code, and payment sources. Every supported value can still be sensitive; applying the source marker is an explicit privacy decision. See the executable multi-person example and LEGEND_SYNC.md for the complete contract and manual-test limitations.

Duplicate Item

Import createDuplicateItem from a11y-repeatable-fieldset/addons/duplicate-item. It creates one native Duplicate button per item and delegates template materialization, fresh identity, insertion, registry order, rollback, focus, status, and the completed item-duplicated event to public instance.duplicate().

Only explicitly marked supported native-control current state is copied, while the trusted-template candidate remains disconnected and before any new-item addon setup. Files, hidden/server state, credentials, payments, errors, validity, disabled/readonly controls, and custom controls are excluded. Try the executable Duplicate Item demo.

Undo Remove

Import createUndoRemove from a11y-repeatable-fieldset/addons/undo-remove. It creates one short-lived native Undo button per root. Core recreates structure from the trusted template with the removed reserved key; the addon retains only current state from explicitly marked supported native controls.

Only the latest committed removal is retained. Expiry pauses while the Undo button has focus. Files are never read, retained, or assigned; hidden server state, passwords, credentials, payments, errors, validity, defaults, disabled/readonly controls, and custom controls are excluded. Try the executable Undo Remove demo.

Remove Guard

Import createRemoveGuard from a11y-repeatable-fieldset/addons/remove-guard. The addon owns the single control-driven Remove-request route. Explicit application policy decides whether to remove immediately or request synchronous or asynchronous confirmation.

Lifecycle events remain completed, non-cancelable observations. Public instance.remove() calls remain immediate approved API commands. The addon itself reads no form values; sensitive-state classification is explicit application policy.

Public hook contract

MemberResponsibility
idA stable, non-empty identifier. Duplicate IDs are rejected during transactional initialization.
setup(context)Optional component setup. It may return one synchronous cleanup callback.
setupItem(context)Optional setup for every discovered or newly added item. It may return one synchronous cleanup callback per item.
context.on(type, listener)Subscribes through the parent instance and returns idempotent cleanup. The parent also tracks the subscription for teardown.
context.onRemoveRequest(handler)Registers the instance’s single control-request owner. It receives a frozen, single-use approved command; no DOM event is added.
context.onRemovePreparation(handler)Registers the independent single removal-snapshot owner. Its commit/rollback object receives a one-shot exact-key restoration command without retaining detached DOM.

Contexts expose structural metadata and core methods, not private implementation hooks or field values. The parent owns every cleanup callback and releases detached item references.

Setup, rollback, and cleanup order

  1. Component setup runs in addon registration order.
  2. Existing-item setup runs in item order, then addon registration order.
  3. New-item setup completes before the public item-added event.
  4. If setup fails, completed work rolls back in reverse order and the command reports addon-error.
  5. Item cleanup runs in reverse registration order before that item is detached.
  6. A removal snapshot commits only after detachment and synchronization stabilize; failed removal rolls it back.
  7. Destroy cleans every current item, then component registrations, all in reverse order.

Cleanup must be idempotent. The parent continues through remaining cleanup callbacks if one callback throws.

Boundaries addons must respect

  • Do not patch private methods, fake core lifecycle events, bypass minimum/maximum rules, or mutate frozen defaults.
  • Do not duplicate core structural announcements or retain detached fieldsets and their values.
  • Do not initialize on import, silently include another addon, or make core accessibility depend on optional code.
  • Use the root’s owner document and realm when creating DOM or events.
  • Keep addon-specific data and cleanup scoped to the owning root and item.

Packaging gate

The Validation Bridge, Legend Sync, Remove Guard, Accessible Reorder, Duplicate Item, Undo Remove, and Form Memory Bridge subpaths passed the implementation, test, documentation, demo, and package-export gate. Any later addon receives a subpath only after passing the same checks. Placeholder exports are intentionally excluded.
