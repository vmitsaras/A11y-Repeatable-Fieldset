Implemented addon, live validation, and error-summary demo

Register repeated controls once and clean them before removal

The Validation Bridge maps each existing or added fieldset to an application-owned validator. Core owns structural focus and announcements; the adapter owns validation errors, summary links, and their cleanup.

Validation Bridge is implemented and opt-in. Import it from a11y-repeatable-fieldset/addons/validation-bridge. It is absent from the main runtime entry and does not import a validator.

Try live validation and review errors

  1. Confirm the saved email and its server message remain present after initialization.
  2. Add Contact 2, leave Name empty, and move focus to Email. The inline error and matching summary link appear without moving focus.
  3. Return to Name and enter a value. After a short pause, its inline error and summary link disappear together.
  4. Leave Email empty and choose Review validation errors. Focus moves to the validation summary, whose link focuses Email.
  5. Remove Contact 2 and confirm its inline errors and summary links disappear before the fieldset is detached. The saved Contact 1 server message remains untouched.

    Adapter contract

    createValidationBridge({
  id: "application.validation",
  registerItem({ item, phase }) {
    return applicationValidator.registerGroup(item.element, { phase });
  }
})

    registerGroup is an application façade in this example. Registration must preserve author/server errors for the existing phase. It installs item-scoped blur and input listeners; its returned cleanup must synchronously unregister target controls, remove those listeners, cancel pending work, restore author attributes, remove generated inline errors, remove error-summary links, and release descendant references.

    Focus and announcement ownership

    • Core alone handles focus after Add and recovery during Remove.
    • The application validator may focus the summary or first invalid field only after an explicit validation review.
    • The bridge creates no structural live region. This demo keeps the synchronized summary silent during live validation and never moves focus to it.
    • A new or changed inline error is the single polite live validation message. Repeated identical errors are not reinserted.
    • During error review, inline errors become non-live before the summary receives focus, avoiding competing validation announcements.
    • This documentation example never submits the form or presents a simulated successful save.
    • Manual screen-reader verification is still needed for the combined validator and structural flow.

    Failure behavior

    • A registration failure during initialization rolls back prior completed registrations and leaves author markup usable.
    • A registration failure during Add removes the incomplete item, returns addon-error, and emits no successful item event.
    • A cleanup failure aborts removal, keeps the item attached, returns addon-error, and emits no successful removal event.
    • Adapters must make partial setup and cleanup internally transactional because core cannot reconstruct an opaque validator registration.

    A11y Form Validator compatibility

    A11y Form Validator 1.0.19 was reviewed for this integration. Its public instance currently provides whole-form refresh(), clearErrors(), and getErrors(), but not item-scoped registerGroup() cleanup.

    refresh() alone cannot clean target errors before detachment, and whole-form clearErrors() can erase unrelated or server errors. The Validation Bridge therefore does not reach into private validator state or claim a zero-configuration direct adapter. Use an application façade only when it can provide the target-only synchronous cleanup contract.
