Completed-operation observations

Lifecycle events

The frozen EVENTS export contains exactly seven names. Events observe completed work; they are not commands and cannot cancel an operation.

Event set

ConstantDOM nameCompleted state
EVENTS.inita11y-repeatable-fieldset:initExisting items, addons, positions, controls, status mechanism, and active registration are ready.
EVENTS.itemAddeda11y-repeatable-fieldset:item-addedThe new item is attached and registered; addons, positions, controls, focus, and status text are stable.
EVENTS.itemDuplicateda11y-repeatable-fieldset:item-duplicatedThe trusted-template item has copied approved state, is attached immediately after its source, and addon setup, positions, controls, focus, and status are stable.
EVENTS.itemRemoveda11y-repeatable-fieldset:item-removedCleanup completed, the item is detached, positions and controls are stable, and required focus recovery finished.
EVENTS.itemRestoreda11y-repeatable-fieldset:item-restoredA trusted-template fieldset with the removed reserved key is attached; addon setup, positions, controls, requested focus, and restored status are stable.
EVENTS.itemMoveda11y-repeatable-fieldset:item-movedThe same attached fieldset has a new adjacent registry and DOM position; snapshots, focus, and status text are stable.
EVENTS.destroya11y-repeatable-fieldset:destroyPlugin-owned resources are gone and current author fieldsets and values remain. This is the instance’s final event.

Shared flags and detail

  • Target: the component root.
  • bubbles: true, composed: false, cancelable: false.
  • Created with the root document’s CustomEvent realm.
  • Every detail contains instance and root.
  • Item events identify stable keys and structural positions/counts without including field values. Add/Remove expose core source and trigger; Duplicate exposes source/new identity and nullable focus; Restore exposes prior/current coordinates and nullable focus; Move exposes direction, prior/current position, and nullable preserved focus.

When events do not fire

  • Saved items discovered during initialization do not emit item-added.
  • Minimum/maximum/Move boundaries, unknown targets, invalid templates/keys, copy failures, and rolled-back operations emit no item success event.
  • Failed initialization emits no lifecycle event.
  • Repeated destroy() calls are silent, and no delayed event may follow destroy.

Consumption guidance

Subscribe to the narrowest event needed and remove application listeners during teardown. Addons should use their parent-provided typed subscription utility so cleanup is registered automatically.

The removed item’s fieldset is detached when listeners receive item-removed. Use it synchronously when necessary and do not retain it or its form data.

The restored item is new trusted-template DOM with the exact reserved removed key. previousPosition describes its pre-removal location and position accounts for intervening structural work. Event detail never contains retained values.

The moved item remains attached with the same key, names, IDs, values, and addon registration. Use previousPosition, position, and direction rather than comparing form values.

A duplicated item is a fresh trusted-template fieldset with a fresh key. item-duplicated is distinct from ordinary item-added so consumers can recognize that explicitly selected current state may have been copied without placing those values in event detail.

Open the lifecycle-event inspector to observe the exact public event set and blocked-operation silence.

Intentionally excluded

The MVP has no before/request DOM events, generic change/count, validation, dirty-state, reset, generic/batch reorder, announcement, or batch events. The narrow completed item-moved, item-duplicated, and item-restored observations exist only for their transactional commands. Remove Guard uses the separate typed context.onRemoveRequest() route; Undo Remove uses the independent context.onRemovePreparation() route. Neither route is a DOM event.
