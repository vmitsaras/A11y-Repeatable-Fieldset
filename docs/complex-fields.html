Identity and reference coverage demo

Add participant profiles with complex form relationships

This dense example exercises the documented token locations across labels, names, radios, descriptions, datalists, table headers, same-page links, and file inputs.

Scenario

A workshop registration form collects several participant profiles. Each profile needs isolated radio choices, reusable suggestions, multiple descriptions, an availability table, notes, and an optional document upload.

Try it

  • Add two profiles and choose different contact methods; selecting a radio in one profile must not clear the other profile’s choice.
  • Inspect the generated labels, list, aria-describedby, headers, and hash-link targets.
  • Remove the first profile and confirm the remaining names keep their original stable keys.
  • Choose a file, add another profile, and confirm the new file input starts empty.

Accessibility notes

  • Each repeated item is the outer participant fieldset; the contact method uses a nested fieldset only because it is a genuine radio group.
  • Radio names contain the stable key, so each participant has an independent browser group.
  • Tokenized local references resolve inside each clone while the shared untokenized description remains external.
  • Table headers describe the availability cell without using table structure as the repeated-item grouping.
  • File inputs always begin empty in generated items and are never assigned, copied, or restored.

Developer notes

The template uses the single literal token only in approved id, name, for, list, ID-reference, hash-link, and item-key attributes. The plugin does not replace visible text or arbitrary data attributes.
