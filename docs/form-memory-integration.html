Form Memory Bridge

The bridge restores repeatable structure before an application-owned draft service restores values. It stores stable keys and order only; storage, consent, expiry, sensitive-field policy, and clearing remain application responsibilities.

The addon is implemented at a11y-repeatable-fieldset/addons/form-memory-bridge. It has no runtime dependency, is absent from the main entry, creates no UI, and never writes to browser storage by itself.

Restore structure before values

  1. Create the bridge with the repeatable root, a stable draft field key, the public core factory, and a save callback.
  2. Pass bridge.draftControlAdapter to createDraftPersistence() on a containing form.
  3. Pause autosave, call drafts.check(), and obtain the user’s restore decision.
  4. Pass the approved record to bridge.initialize(). It validates versioned keys, adds only missing trusted-template items, preserves current server items, and initializes core once.
  5. Call drafts.restore({ force: true }) so native values resolve against the now-complete field names and IDs.
  6. Resume autosave and synchronize validation only after structure and values are stable.

The draft package’s generic restore-prompt addon calls restore() directly and cannot insert this required structural phase. A structure-persisting application must own or wrap the restore-decision UI.

Integration outline

import {
  createDraftPersistence,
  type DraftPersistenceInstance
} from "a11y-form-draft-persistence";
import { createRepeatableFieldset } from "a11y-repeatable-fieldset";
import { createFormMemoryBridge } from
  "a11y-repeatable-fieldset/addons/form-memory-bridge";

let drafts: DraftPersistenceInstance | undefined;

const memory = createFormMemoryBridge({
  root,
  fieldKey: "application:contacts:structure",
  createInstance: createRepeatableFieldset,
  save: () => drafts?.save()
});

drafts = createDraftPersistence(form, {
  formVersion: 1,
  key: "application:123:v1",
  expiresAfter: 604_800_000,
  restoreStrategy: "prompt",
  customControlAdapters: [memory.draftControlAdapter]
});

drafts.pause("repeatable-structure-setup");
const checked = await drafts.check();
const record = checked.status === "available" && userApproved
  ? checked.record
  : undefined;
const initialized = memory.initialize({
  ...(record === undefined ? {} : { record }),
  repeatableFieldsetOptions: { minimum: 1, maximum: 8 }
});

if (initialized.ok && record !== undefined) {
  await drafts.restore({ force: true });
}

drafts.resume("repeatable-structure-ready");

The containing form—not the repeatable root—must be the draft-persistence root because custom-control discovery scans descendants. See FORM_MEMORY_BRIDGE.md for failure handling, cleanup, and typed outcomes.

Conservative merge and failure policy

  • Saved keys and order are restored, but current server or author items absent from the draft are preserved after them.
  • No current fieldset is deleted and no live fieldset is cloned.
  • Over-maximum, duplicate-key, unknown-version, malformed, template, or ID failures do not leave partial prepared structure.
  • If core initialization fails after preparation, original item-container children are restored before the error is rethrown.
  • A missing structure field initializes current markup normally, which supports older drafts for controls already present.

Privacy and data exclusions

  • Require explicit application opt-in, a clear retention period, and an accessible way to clear saved data.
  • Exclude passwords, payment details, authentication secrets, and other sensitive fields by default.
  • Never read, serialize, assign, or claim to restore file-input values.
  • The bridge snapshot contains keys and order only—not values, server errors, focus, live-region text, or HTML.
  • Scope storage and field keys to the application, form, account/session policy, and schema version; browser storage can disclose data on shared devices.

Lifecycle and evidence limits

The addon coalesces only completed structural events into the supplied save callback. It creates no second announcement, focus move, event, timer, or UI. Parent cleanup makes queued callbacks inert and never destroys the application-owned draft instance.

Cross-tab structural updates are not applied to an active repeater. A containing application must choose a reload or safe reinitialization policy instead of mutating live structure from a storage event.

Automated coverage verifies structure, rollback, cleanup, package isolation, and Pages wiring. Real-browser review remains required for storage denial, autofill, page lifecycle, cross-tab behavior, keyboard flow, screen-reader output, zoom/reflow, and shared-device privacy copy.
