Implemented Legend Sync addon

Review several household members without losing who is who

This edit form starts with three completed people. Their stable keys and backend names stay unchanged while the packaged Legend Sync addon updates each legend after a full-name change is committed.

Scenario and user goal

A benefits coordinator needs to review a household, correct one person’s details, add a missing member, and remove a duplicate without confusing visible order with saved identity.

Try it

  • Navigate through all three fieldsets and compare the distinct legends with a one-item demo.
  • Edit a full name, move focus away to commit the change, and confirm only that item’s legend changes.
  • Add a person and confirm focus moves to the new full-name field.
  • Remove the middle person and confirm the remaining names and stable form-control names are not renumbered.

Implemented, opt-in addon

Legend Sync is packaged from an explicit subpath. This page imports createLegendSyncAddon from the copied ./assets/legend-sync.js build. The addon is never enabled by the core entry and creates no additional live region.

Accessibility notes

  • Each repeated group is a real fieldset with a distinct, non-empty legend.
  • Native Tab order follows the document; the component adds no composite-widget keyboard pattern.
  • Core owns focus after Add and Remove plus the single polite structural status region.
  • The name summary is not a live region. Assistive technologies may expose a changed legend differently, so test this concept in target browser and screen-reader combinations.
  • A full name can be personal data. Mark a source only after deciding that repeating its value in the visible and accessible legend is appropriate.
  • The page has no structural motion; reduced-motion preferences do not hide any state.

Developer notes

  • The root, items, template, action, key, position, focus, and status selectors are the documented public data attributes.
  • The runtime and optional package CSS come from copied build assets under ./assets.
  • The demo imports the explicit ./addons/legend-sync build and passes it through createRepeatableFieldset(root, { addons }).
  • The addon listens only to [data-a11y-repeatable-fieldset-legend-source] on committed change, updates the dedicated [data-a11y-repeatable-fieldset-legend-value] suffix, and returns idempotent cleanup.
  • Visible positions change after removal; stable keys, IDs, and names do not.

Evaluation limits

Automated tests verify the marker contract, committed update timing, cleanup, privacy exclusions, and absence of a second status message. A 2026-08-31 VoiceOver + Safari recording produced a partial result: Add was announced, but a committed legend value and a surviving renumbered legend were later exposed with stale group context, and the middle-item Remove confirmation was not captured. Isolation reproduced the stale native fieldset name with Legend Sync enabled and disabled, so the addon is not established as the cause. This scenario remains open and is not recorded as passing. Long values are not truncated; applications must choose a concise source and appropriate length policy.
